## 先看一个尴尬的事实

GitHub 上 88% 的 JavaScript 仓库 star 数是 **0**（我用搜索 API 实测的分布）。其中相当一部分是能跑、有测试的"好项目"——它们缺的不是代码质量，是**前 10 秒**。

访客点进你的仓库，扫一眼、决定去留。这个决策窗口里，能救你的信息非常少：仓库描述、首屏 README、有没有一张图、能不能 30 秒内复制一条安装命令。大部分仓库死在这些地方。

我写了一个工具把这些"死亡点"固化成检查，先看诊断报告长什么样：

```
  ⚡ 最值得先做的三件事
  1. [HIGH] 安装命令靠近顶部
     第一条可复制的安装命令在第 62 行
     → 把安装命令提到 README 首屏
  2. [HIGH] 首屏有截图 / GIF / Demo 图
     只有徽章类图片——没有真正的截图 / demo / 主视觉
     → 把截图放到 README 前 ~40 行
  3. [MED] Issue 模板
     没有 issue 模板
     → 加 .github/ISSUE_TEMPLATE
```

每条结论都带证据（第几行、几个、哪天），你可以不同意，但没法忽视。

## 实测三个著名仓库，问题很有意思

工具叫 `why-no-stars`，拿几个你肯定用过的仓库试了试：

**sindresorhus/got（93/100，S 级）**——GitHub 上打磨最精致的仓库之一，居然也有问题：它的 logo 是 HTML `<img>` 写的，第一张 Markdown 图片是**藏在 HTML 注释里的 codecov 徽章**。工具的解析器如果能见注释里的内容，就会产生"有/没有首图"的误判——这本身就是大多数 README 检查工具的通病：把"源码里有"当成"访客能看到"。

**torvalds/linux（65/100，C）**——最能暴露这类工具的傲慢。它 20k+ 贡献者的 API 会 403，很多工具会报"0 贡献者"；它的 GPL COPYING 不被 SPDX 识别，很多工具会喊"没有 license = 法律上不可用"；它的测试在 `tools/testing/`，根目录扫描看不到。我的处理是：**拿不到的数据标记"跳过"并说明原因，绝不计零分**——一个诊断工具编造证据比没有工具更糟。

**expressjs/express（93/100）**——分位线显示它超过 99–100% 的 JavaScript 仓库。但安装命令在 62 行，首屏没有一张真图（全是徽章）。S 级仓库照样有可执行清单。

## 它怎么打分（比"玄学打分"多一步）

六大支柱：第一印象(25) / 快速上手(20) / 信任维护(20) / 社区健康(15) / 可发现性(10) / 增长势头(10)。32 项检查，每项返回 pass / warn / fail / skip，全部带证据和修复动作。

两个设计点：

1. **QuickWins 按"能找回多少分"排序**（支柱权重 ÷ 该支柱检查数），并且按根因去重——"没有安装命令"和"安装命令太靠下"是同一个问题，不该占两个推荐位。
2. **生态分位**。这是同类工具没有的：用搜索 API 统计你主语言全部仓库的 star 分布（0 / 1–2 / 3–9 / 10–99 / 100–999 / 1k–10k / 10k+ 七个桶），告诉你诚实区间。0 star 仓库还会拿到背景："90% 的同类仓库是 0 star，中位数仓库：0"——这不是安慰，是校准。

## 用法

```bash
# 免安装，Node >= 18
npx github:paopaonb666/why-no-stars <用户名/仓库>

# 常用输出
npx github:paopaonb666/why-no-stars me/my-project --svg scorecard.svg  # 可分享评分卡
npx github:paopaonb666/why-no-stars me/my-project --md report.md       # 可贴 issue 的报告
npx github:paopaonb666/why-no-stars me/my-project --zh                 # 中文
```

无需 API key；配 `GITHUB_TOKEN` 从 60 次/小时提到 5000 次/小时。零依赖、纯本地分析、不上传代码。

## 它给自己体检只有 85 分

这是工具审计自己的真实报告（发布当天）：三大支柱 90–100，但**增长势头是 0**——因为当天刚发布、没有任何 star。工具拒绝装糊涂，报告里明说"这个支柱你自己修不了"。
