## 正文（原样粘贴，Markdown）

```markdown
先说背景：我给自己的项目做完之后看了眼 star 数，突然意识到一个问题——我的仓库缺的不是推广，是"前 10 秒"。

访客点进一个 GitHub 仓库，扫一眼、决定去留。而 README 里最常见的死法是：安装命令埋在第 60 行、首屏没有一张图、没有 license、214 天没提交。这些全是可量化的。

于是我写了个工具把这些检查固化下来：**why-no-stars**，一条命令体检任意公开仓库：

```
npx github:paopaonb666/why-no-stars <用户名/仓库>
```

免安装、零依赖（Node >= 18 就能跑）、不需要 API key（配 GITHUB_TOKEN 更好）。

**它做什么：**

- 32 项检查，六大支柱：第一印象 / 快速上手 / 信任维护 / 社区健康 / 可发现性 / 增长势头
- 每条失败项都带证据，比如"第一条安装命令在第 71 行"、"0 个徽章"、"214 天没提交"——不是玄学打分
- 按"修了能找回多少分"排序，给你最值得先做的三件事

**别家没有的：生态分位。** 它用 GitHub 搜索 API 统计你主语言所有仓库的 star 分布（0 / 1–2 / 3–9 / 10–99 / 100–999 / 1k–10k / 10k+ 七个桶），告诉你诚实区间。比如 sindresorhus/got 是 "star 数超过同类仓库的 99–100%"。区间不是点值——因为你只知道自己在哪个桶里，工具不装精确。

**几个实测（挺有意思）：**

- `sindresorhus/got`：93/100 [S]。GitHub 上打磨最精致的仓库之一，照样被挑出"安装命令在 71 行"
- `torvalds/linux`：65/100 [C]。工具会诚实标注：无包清单的项目在生态特定检查上给温和判定，不瞎猜
- 它自己给自己体检只有 85/100，增长势头诚实地是 0（刚发布没 star）——工具拒绝装糊涂

**它不做什么：** 不测代码质量（那是另一回事，分数是"店面"的待办清单，不是工程水平的审判）、不上传任何代码、没有 LLM，全是本地正则 + API 元数据，错了就是 bug。

开源 MIT，GitHub：https://github.com/paopaonb666/why-no-stars

欢迎拍砖，尤其欢迎"你这个检查阈值不合理"类的 issue——加一个新检查只要 30 行。
```
